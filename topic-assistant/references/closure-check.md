# 尾端收拢与关键资料验收

角色 2 先用短记录明确设计，角色 3 在最终联网核验后、长综述和语言审校之前完成一次实质复核。复用原资格审核、既有资料和原检索预算；不增加角色、日志、联网轮次或全文重读。最多一次定点修订，计入既有修复/回退额度；仍不成立就剔除或如实限缩，不连续重试。

## 唯一准入标准：先短设计，后长报告

角色 2 在既有 topics.json 写短设计，角色 3 对照实际来源复核下列五项。其他文件的资格、题名、可行性与收拢要求均引用本处，不另设一套准入清单。六项 qualification.checks 和原有 JSON 字段继续使用，不新增日志或打分表。

| 核心判断 | 必须说明的内容 | 既有记录位置 |
| --- | --- | --- |
| 研究范围 | 实际地域/机构、对象、事项、时段和单位；材料范围与建议对象对应 | scope、scope.selection、decision.actor |
| 学术增量 | 已有答案之外仍需分析什么，比较或论证怎样产生新认识，什么证据会推翻原设想 | research_value、question、theory |
| 材料可得性 | 当前问题必需的样本及字段是否真实可读，权限、规模、期限等关键条件是否已核 | observables、data_checks、conditions |
| 评价依据 | 判断规则来自哪里，适用于哪些层级、文种与主体；理论如何改变比较或判断 | criterion_basis、applicability、theory_use |
| 结论边界 | 题名承诺与证据相称；不同结果分别由谁调整什么，无差异时是否允许不调整 | inference_level、allowed_conclusion、decision_links |

学术增量不成立、范围待定或当前设计自相矛盾的题不得入选；不能靠标 draft 保留。学术问题成立而关键条件待核的题可有条件入选。材料已证实无法取得则退出当前设计。只有样本、实施条件和实质审核都支持时才可确认可行。

最终联网和本次唯一一次实质复核结束后、撰写长综述前，执行 `validate_run.py preflight <运行目录>`。它复用既有设计、样本、状态和排序检查，不读取论文、不联网、不要求已生成报告、不自动写入“通过”。报错时在既有一次修订额度内处理；未解决则按真实缺口交付阶段草稿，不能绕过错误继续宣称最终题已确认。此命令不能代替上述五项判断。

## 判断依据与证据边界

每题只有一个核心判断，能说明“根据什么观察、按什么依据作何种判断、由谁据此调整哪一环节”。题名、理论名、编码表、统计表和“提出优化建议”不能代替这个判断。选题阶段交付的是可回答的问题和判断规则，不是捏造已经成立的研究发现；允许无效、反向、无差异或条件不同的结果，并同步改变建议。

实际研究范围在准入前固定：具体地域、群体/机构、事项、时段、分析单位须相互对应；列出本次实际选定的单位及选择依据。“以后选某省”“选能打开的城市”“任选一个一件事”不是固定范围。可以研究全国某一明确机构层级或制度问题，不机械强制单一城市；匿名真实案例有依据即可。尚待用户确定范围的候选不进入最终名单。

结论分为文本判断、关联、机制、效果。政策文本研究可得明确而有用的文本结论，不强制访谈或实验；但条款次数只能直接说明文本呈现，不能直接说明内部协商成本、人员心理负担或真实绩效。相关关系不能冒充激励造成的因果结果。机制解释需要过程证据；效果判断需要结果测量及可信的识别安排，仅有结果字段仍不自动成立。文本内机制安排的分析用 text 并限于制度设计，不冒充实际运行机制。

规范性“缺失、不足、应当增加”的判断须说明评价依据及适用层级、主体、文种和条件；不能仅以数量较少推出不足，不能把对某类文件的要求无条件施加于另一类文件。判断依据可以来自适用规则、明确理论标准或有论证的比较基准。不能把已有规定原样重述成新发现或据非标准材料直接推出合法豁免、容缺等处置。

### 学术增量与适用条件

先用本次已读材料区分“原文已经回答什么”与“仍需研究什么”。若核心问题只需摘录某条现行规定即可回答，计划只是重排条款、做情形表或换成问句，不作为论文选题推荐。题名改成“机制、路径、优化研究”或预分配论文字数都不能补足学术问题。即使资料齐全、管理落点明确，也不能因此通过准入。

文本研究可以成立：例如澄清不同规则的适用冲突、按有论证的标准比较制度安排、解释制度差异、检验概念分类或论证规范取舍。须具体交代已有回答之外的待解问题、比较/论证怎样产生新增认识，以及可能推翻原设想的材料或理由；结果可以是规则并无冲突、无需调整。不能只把这些贡献名称填入字段。篇幅由问题、分析及证据支撑，不强制大样本、访谈、因果识别、文件数量或方法组合，也不把不能进机关误解为只能逐句抄政策；公开二手资料能否使用按实际约束判断。

理论必须在本题承担可检查的工作：用概念区分什么、为何按某标准比较、解释哪种差异或支持何种规范取舍；与既有 theory.observables/method_fit、judgment_rule 和 criterion_basis 衔接。只写理论名称、概念定义或泛泛“降低负担”不算适配；不机械用“删掉理论名称”作为否决测试。

问题依据可为事实、文献争议或待检验风险。风险未被证实本身不否决，但必须有识别其是否存在的材料和可回答的设计；不能把“可能发生重复提交”写成已发生的问题，再据此要求修改办事指南。原文未提及某安排，应记未说明/无法据此确定，不能自动编码成“仍须提交”“存在缺陷”。从适用规则作出的推断须明确标为推断并说明依据、适用条件；“上传备查”等表述本身不推出合法免交。政策要求、文本规定与实际执行分别判断，不能相互替代。

只把回答当前核心问题必需的资料放入 observables、data_checks、conditions 和 unresolved 的关键缺口。无关地区的指南、超出文本研究的调用日志、效果数据等，不因“将来有用”而采集或列为本题可行性的前提。确有价值的后续扩展可在主要风险/边界简述并明确非本题要求，不另建清单、不增加检索，也不据此降低当前设计的状态；覆盖边界仍如实说明。若删去某资料会改变当前问题或结论，它就是核心资料，不能改叫扩展来绕过核验。

### 简短对照案例

- **规定查答：**一份现行文件已明确何时人工审核，研究只是重排条款并改称“机制研究”，没有新的比较或论证问题，应剔除。题名、表格及篇幅不构成研究增量。
- **规范文本比较：**比较指引、技术文件与地方办法时，先说明各自适用对象、效力性质和职责分工，再判断具体责任衔接是否存在冲突、授权细化或无法确定。允许得出分工合理、无需增补的结论；不能要求每种文件写齐同一套要素，也不能从一个区推广到全部省级部门。真正的比较和规范取舍可以构成论文，不强制增加内部数据。
- **答复质量与实际减负：**与官方指南核对真实 AI 答复可判断信息错误、缺漏及转人工条件；没有用户成本测量时不能直接回答“是否降低学习成本”。可在原修订额度内将问题和题名一致限缩为信息质量，重新准入；若要保留实际减负问题，则必须核实相应结果测量与设计条件，不能只换措辞。
- **未核不等于失败：**问题和评价标准成立，已确认平台入口但尚未取得完整答复，可标有条件可行并说明先行小测。已完整取得条款但比较结果无缺口，也可形成有研究依据的“不必增补”结论；不得为了凑优化建议强行增加审计、培训或留痕要求。

这些案例解释判据，不限定实际题目或固定结论。理论用来论证标准及取舍，不能替代证据；没有理由认为“多加条款”必然更好时，不作此建议。

## 在既有记录中连接判断与证据

合格候选在 topics.json 内补充：

1. `scope.selection:{status:"fixed",units:["实际选定的地域/机构/事项等单位"],basis:"选择依据"}`。待定范围标 pending 并判 ineligible，不填空泛代称凑 fixed。
2. `closure:{research_value,inference_level,core_judgment,judgment_rule,criterion_basis,applicability,allowed_conclusion,limits,observables,decision_links}`。research_value 写 `{question_status,known_answer,open_question,new_knowledge,theory_use}`：question_status 为 requires-analysis/answered-by-source/unassessed，依次为仍需实质分析、已被来源直接回答、尚未判断；其余四项分别简述已有回答、尚待解决的分析问题、预期新增认识及理论的实际作用。只有 requires-analysis 可判 eligible；其余剔除或在既有一次修订内改题后重新准入，不得仅把状态改为通过。judgment_rule 沿用本次具体分析办法，不另写重复方案。inference_level 为 text/association/mechanism/effect；其余字段用简短具体说明，limits 写出不能推出的结论。core_judgment 是一个待判断问题，judgment_rule 是判断办法，criterion_basis 是标准依据，不填写套话。
3. `observables` 每项 `{observable_id,variable,definition,unit,required_form,required_fields:[]}`，只列回答核心问题不可缺的观察量，避免罗列所有可能变量。required_form 为 document/item/paired-versions/matched-records/process-record/outcome-measure。历史变化用 paired-versions；时滞与回复内容的关系用 matched-records，required_fields 至少包含同条记录的留言日期、回复日期、回复正文及匹配标识；机制用 process-record；效果用 outcome-measure。字段名据真实资料填写，不以“有数据”概括。
4. `decision_links` 每项 `{observable_ids:[],condition,action,basis,applicability}`，把判断条件、具体措施、措施依据及适用范围连接起来；覆盖全部核心观察量。替代/无效结果沿用 decision.alternative_result，不再复制一套清单。措施效果未经检验就写建议及验证条件。

最终核验在 web-feasibility.json 对应 result 增加 `data_checks`；每个 observable_id 恰有一项 `{observable_id,status,reason,samples:[]}`。status 取 verified/unverified/unavailable，分别表示已核代表性样本及设计所需字段、尚未核清、已证实关键材料无法取得。网络失败属于 unverified，不等于已证明材料不存在。小样本核验不是全量数据已取得，规模、覆盖、权限仍在原 checks/unresolved 说明。

每个 sample 记 `{source:{kind,ref},locator,observed,unit_key,form,fields:[]}`。kind=web 时 ref 是本题实际访问的 source URL；kind=hotspot 时为本题明确复用的 web_id；kind=local 时为允许输入中已登记的 source_id，并补 evidence_ids 指向台账中的实际全文位置。locator 和 observed 写出实际看到的事项、条款、字段或记录，不只复述网站名称。fields 只列实际读到的字段，form 对应所需材料形态；样本真实内容仍须执行者核对，脚本不会自动读取网页或判定声明真假。

历史版本样本另外记 version_key：同一 unit_key 至少两份不同版本，分别标真实版本及位置。不同省、不同事项、单流程与集成流程、不同目的的文件不能假扮前后版本；异类文种比较须解释可比性，不能冒称时间变化。matched-records 必须核同条记录的日期与正文，不能把网站开放时间当回复时滞。政策背景、首页、目录、摘要和题录均不能替代事项明细、配对版本、过程或结果样本。可以复用已核热点/指定论文中的真实数据样本，但学术文章只有在实际展示所需材料时才算样本，讨论同一主题本身不算。

## 状态与改题

只有所有核心观察量均有合格样本、关键访问和实施条件也已核清，才可 confirmed/建议做；不能仅凭官网可打开、政策已发布或搜索摘要完成确认。缺口未核清时只能 conditional/unavailable、调整后再做/暂无法判断，最终报告保持 draft，并在本题资料小节写“关键资料待核”及具体缺项。已证实核心材料无法取得的当前设计须 not_feasible 并退出最终名单；不以条件式措辞挽留无法回答的问题。

备用方案只改变采集方式且仍能回答同一问题时可保留；删去日期、删去结果变量、换事项/地域或从机制改为纯文本等实质改题，要同步改题名、问题、观察量、结论边界、理论与建议，并在既有 qualification.reason 记改动及重新准入理由，重新核对当前证据。使用既有一次修订额度，不重开检索、不从淘汰题补位；无法在额度内核清就降级或剔除。

角色 3 结合实际来源完成语义复核，在 closure.review 写 `{status:"supported|limited|inconsistent",reason,design_sha256}`。先实质复核 research_value：对照已知回答、待解问题、分析办法、理论作用及新增认识，不能仅接受角色 2 的 requires-analysis 声明；若仍是条款查答或无研究增量，将资格改为 ineligible 并写具体原因，不能以 limited/待补证保留。同时按[正式学术题名规则](agent-2-topic.md#最终题名采用正式学术表述)检查题名是否准确、范围明确、承诺与设计相称，不靠改名补救实质缺陷。supported 表示当前设计与证据边界可衔接，不表示研究假设为真；limited 只用于学术问题成立但有明确待核条件的设计，仅可 draft；inconsistent 不得最终入选。reason 用一段短说明涵盖学术问题是否成立、核心判断能否由所需资料回答、措施依据是否适用、是否存在越界推断和无关扩展条件，不能只写“已检查”。复用此一次审核，不另增评审轮次。脚本只核声明、对应及指纹，不能判断文字是否真的构成学术贡献；不得把校验通过宣称为学术质量已获证明。

后续否决沿用[角色 3 的快照与剔除约定](agent-3-feasibility.md#去-ai-化之前筛选前五)，不回写原排序或删除已核记录。联网不可用时若凭已读本地材料确认学术问题不成立，可记上述后续否决，题目结果为 not_feasible，联网整体仍为 unavailable；理由须说明否决来自本地审核，不能冒称联网确认。

设计定下后，`validate_run.py design-data <运行目录>` 给出当前设计摘要，实际复核完成后才登记 design_sha256。题名、问题、范围、理论、结论或措施变化会使原复核失效；命令和哈希不是学术批准。写长综述前完成该次复核，正文冻结后仍只做原有一次全文语言审校。最终 Markdown 用自然语言展示“结论与证据对应”，不暴露内部 ID/哈希，也不把这张设计表放入文献综述。
